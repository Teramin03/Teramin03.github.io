CentOS Stream 9 から 10 への移行 2026

0. この備忘録について

0.1. 目的

WSL2上で稼働していたCentOS Stream 9を、CentOS Stream 10へ移行した際の記録である。 同種の作業を再度行う際に、方式の検討からやり直さずに済ませることを目的とする。

今回は、新しいイメージを別途導入し、必要なものだけを移送する方式を採った。 理由は1章に記す。

0.2. 前提としたもの

  • 移行先のCentOS Stream 10が、別の登録名で導入済みであること
  • 移行対象のリポジトリがGitHub側へ反映済みであること
  • 管理者権限でPowerShellを実行できること

0.3. 扱わなかったこと

  • リポジトリ以外の開発環境の移送。
  • Ubuntu側の整理。同じ手順で処理できるため本稿では省いた

0.4. 表記について

  • PS> で始まる行はWindows PowerShellへの入力である
  • $ で始まる行はCentOS側のシェルへの入力を示す
  • <...> で囲んだ箇所は自分の値に置き換える
  • 各節末尾の枠は、実際に手元で実行して確認した内容の記録である

0.5. 作業した環境

CentOS Stream 9 のサポート終了は2027年5月末である。 期限までは余裕があるが、移行の手間は環境が育つほど増すため、早めに済ませた。

1. 移行方式の検討

1.1. その場での版数更新は可能か

CentOS Streamはdnf system-upgrade に相当するものは無い。

1.2. 採った方式

以上より、次の方式を採った。

  1. 移行元を丸ごと書き出して退避する
  2. 移行先のイメージを別の登録名で導入する
  3. 設定ファイルのうち再生成が面倒なものだけを移送する
  4. リポジトリは移送せず、移行先で取得し直す
  5. 動作を確認してから移行元を削除する

移行元を残したまま移行先を構築できるため、失敗しても損失が生じない。 両者は独立した登録としてそれぞれ存在する。

2. 移行前の書き出し

2.1. 登録済み一覧の確認

まず登録名を確定させる。以降の操作で繰り返し使うためである。 

PS> wsl -l -v

移行元と移行先の双方が並んでいることを確認する。 .wsl ファイルをダブルクリックで導入した場合、 登録名は CentOSStream-10-Alt のような既定値となる。

2.2. 書き出し

PS> mkdir C:\wslbackup
PS> wsl --export CentOSStream-9-Alt C:\wslbackup\cs9.tar
PS> dir C:\wslbackup

数分を要する。応答が止まったように見えるが、そのまま待つ。 このtarがあれば wsl --import でいつでも移行元を復元できる。

移行元に触れる前に書き出しを済ませる。 この順序を守っている限り、以降の作業で取り返しのつかない状態にはならない。

確認02

wsl --export は「エクスポートが進行中です。(2684 MB)」と表示した後、 正常に終了した。 dir で約2.6GBのtarが生成されていることを確認した。

3. 移行先の確認

3.1. 起動とユーザの確認

PS> wsl -d CentOSStream-10-Alt

初回起動時にユーザ名を尋ねられる。 移行元と同じ名前を入力する。 異なる名前とした場合、/home/ 配下のパスが食い違い、後の作業が煩雑になる。 

$ whoami
$ cat /etc/centos-release

想定したユーザ名とリリースが返ることを確認したら exit で抜ける。

プロンプトが ~ ではなく /mnt/c/Users/<Windowsユーザ名> となっている場合があるが、 PowerShell側の現在位置を引き継いだだけであり、異常ではない。

確認03

whoami が移行元と同じユーザ名を返し、 cat /etc/centos-release が 「CentOS Stream release 10」を返すことを確認した。

4. 移行元からの退避

PS> wsl -d CentOSStream-9-Alt

4.1. 何を移すかの判断

ホームディレクトリを ls -a で確認し、移すものと移さないものを分ける。

対象扱い理由
.ssh/移送する鍵の再発行と公開鍵の登録が手間であるため
.gitconfig移送する設定量は少ないが移した方が早いため
.bash_history移送する過去のコマンドを引き継ぐため。任意
リポジトリ移送しないgit clone で再取得する方が確実であるため
.bashrc, .bash_profile移送しない追記した行のみを手動で移す。
.vscode-server移送しない接続時に自動生成される。
.dotnet移送しない導入し直す。
.cache, .lesshst移送しない再生成されるため不要

4.2. リポジトリの状態確認

移送しない以上、未反映の変更が残っていないことを先に確かめる。 

$ cd ~/<作業ディレクトリ>/<リポジトリ名>
$ git status
$ git remote -v

確認すべきは次の2点である。

  • nothing to commit, working tree clean かつ up to date であること
  • 取得元のURLが git@github.com: 形式か https:// 形式か

未反映の変更があれば、先に git push まで済ませておく。

4.3. tarによる退避

$ tar czf /mnt/c/Users/<Windowsユーザ名>/Desktop/wsl-migrate.tar.gz -C ~ .ssh .gitconfig .bash_history
$ ls -lh /mnt/c/Users/<Windowsユーザ名>/Desktop/wsl-migrate.tar.gz
$ tar tzf /mnt/c/Users/<Windowsユーザ名>/Desktop/wsl-migrate.tar.gz

-C ~ を与えているため、実行時の現在位置は問わない。 ホームディレクトリを起点として指定した3つが格納される。

エクスプローラは用いない。 Windows側のファイルシステムを経由するとパーミッションが失われ、 .ssh が使用不能となるためである。 tarであれば権限情報が保持される。

tar tzf で中身の一覧を表示し、想定したファイルが揃っていることを確認したら exit で抜ける。移行元に対する操作はここまでである。

確認04

git status が clean かつ up to date であること、 取得元が git@github.com: 形式であることを確認した。

生成されたtarは1.9KBであり、 tar tzf により .ssh/id_ed25519, .ssh/id_ed25519.pub, .ssh/known_hosts, .gitconfig, .bash_history が格納されていることを確認した。

5. 移行先への復元

PS> wsl -d CentOSStream-10-Alt

5.1. 展開

退避時と異なり -C を与えないため、現在位置がそのまま展開先となる。 ホームディレクトリへ移動してから実行する。 

$ cd ~
$ tar xzf /mnt/c/Users/<Windowsユーザ名>/Desktop/wsl-migrate.tar.gz

5.2. 権限の修正

$ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/id_ed25519
$ ls -l ~/.ssh

秘密鍵が -rw------- であることを確認する。 権限が緩いとSSHは鍵の使用を拒否する。 tarを用いた場合は元の権限が保たれているが、念のため確認する。

5.3. gitの導入と疎通確認

$ sudo dnf -y install git
$ ssh -T git@github.com

鍵にパスフレーズを設定している場合は入力を求められる。 Hi <アカウント名>! You've successfully authenticated, ... が返れば鍵の移送は完了である。

確認05

展開後、ls -l ~/.ssh にて秘密鍵が -rw------- であることを確認した。 ssh -T git@github.com はパスフレーズを求めた後、 認証に成功した旨を返した。

6. リポジトリの再取得

$ mkdir -p ~/<作業ディレクトリ>
$ cd ~/<作業ディレクトリ>
$ git clone git@github.com:<アカウント名>/<リポジトリ名>.git

移送ではなく取得し直すことで、権限や改行コードに起因する差異が生じない。 取得後、移行元と同一の状態であることを確かめる。 

$ cd <リポジトリ名>
$ git log --oneline -3
$ git status
$ git config --get user.name
$ git config --get user.email

最新のコミットが一致し、working tree clean であれば移行は完了である。 git config の2つは .gitconfig の移送が効いているかの確認である。

6.1. Visual Studio Codeの再接続

Windows側のVS Codeにて Ctrl+Shift+P を押下し、 WSL: ディストリビューションを使用して WSL に接続 から移行先を選択し、押下する。 .vscode-server は自動生成される。 拡張機能は導入し直しとなるが、設定の同期を有効にしていれば復元される。

確認06

git log --oneline -3 が移行元と同一のコミットを返し、 git status が clean であることを確認した。 VS Codeからの接続も正常に行えた。

7. 移行元の削除

7.1. 退避ファイルの削除

デスクトップに置いたtarには秘密鍵が含まれている。 復元を終えたら速やかに削除する。 

PS> del C:\Users\<Windowsユーザ名>\Desktop\wsl-migrate.tar.gz

7.2. 既定の切り替え

PS> wsl --set-default CentOSStream-10-Alt

以後、wsl と入力するだけで移行先が起動する。

7.3. 登録の解除

PS> wsl --unregister CentOSStream-9-Alt
PS> wsl -l -v

--unregister は仮想ディスクごと消去する。確認は求められない。 ただしこの時点では2.2 で書き出したtarが残っているため、 wsl --import による復元は可能である。

7.4. 書き出しの削除

PS> del C:\wslbackup\cs9.tar
PS> rmdir C:\wslbackup

これを実行した時点で、移行元は完全に失われる。

確認07

wsl -l -v の一覧から移行元が消え、 移行先に既定を示す * が付いていることを確認した。

8. 日本語ロケールの設定

8.1. 言語パックの導入

イメージには英語の最小構成しか入っていないため追加する。 英語ロケールも併せて入れておく。 

$ sudo dnf -y install glibc-langpack-ja glibc-langpack-en
$ rpm -q glibc-langpack-ja

8.2. ロケールの指定

設定ファイルへ直接記述する。 localectl は用いない。 

$ echo 'LANG=ja_JP.UTF-8' | sudo tee /etc/locale.conf
$ echo 'export LANG=ja_JP.UTF-8' >> ~/.bashrc

~/.bashrc にも記述しているのは、 WSLでは /etc/locale.conf が読まれない場合があるためである。

8.3. 反映

設定を書いただけでは、実行中のシェルには反映されない。 一度WSL全体を停止してから入り直す。 

$ exit
PS> wsl --shutdown
PS> wsl
$ locale
$ date

LANG および LC_* の全項目が ja_JP.UTF-8 となり、 date の出力が日本語となれば完了である。

8.4. タイムゾーン

設定は不要。

確認08

wsl --shutdown の後、locale の全項目が ja_JP.UTF-8 となることを確認した。 date は「2026年 8月 8日 土曜日 19:12:54 JST」を返した。

9. 詰まった点と対処

9.1. 設定ファイルを書いてもlocaleが変わらない

/etc/locale.conf と ~/.bashrc に記述した直後に locale を実行しても、en_US.UTF-8 のままであった。

不具合ではない。環境変数は新しいシェルの起動時に読まれるため、 実行中のシェルには反映されないという仕様である。 wsl --shutdown を経て入り直せば反映される。

9.2. apt系のコマンドが通らない

Ubuntu向けの手順を流用すると生じる。対応は次の通りである。

Debian系CentOS
apt install language-pack-jadnf install glibc-langpack-ja
apt install language-pack-endnf install glibc-langpack-en
update-locale LANG=.../etc/locale.conf へ記述

9.3. パスワードは設定しなかった

WSLイメージのユーザはパスワードが未設定で、sudoが無条件に通る設計である。 passwd で設定すると、以後 sudo のたびに入力を求められる。

wsl -d で入る時点でWindowsのログインを通っているため、 設定は不要と判断し見送った。 sshdを立てて外部から接続する場合は必須である。
